# AutoHeal DevOps — User & Operator Guide

**Version:** 1.0.0 (Release Candidate v0.1.0-rc1)  
**Applicability:** SREs, DevOps Engineers, System Administrators, Pilot Evaluators  
**Interface:** Next.js 16 Web Dashboard (`http://localhost:3000`)

---

## 1. Navigating the AutoHeal Web Interface

The AutoHeal DevOps dashboard features an operator-focused dark navy theme (`#0B0F19` background with `#111827` cards) optimized for low-fatigue incident monitoring.

### Main Navigation Structure
- **Dashboard (`/dashboard`):** High-level operational overview, active incidents, service SLO health, and MTTR telemetry.
- **Incidents (`/dashboard/incidents`):** Real-time incident queue, filtering, triage status, and historical resolution logs.
- **Incident Details (`/dashboard/incidents/[id]`):** In-depth incident telemetry, timeline events, AI root-cause analysis, and recovery approval controls.
- **Recoveries (`/dashboard/recoveries`):** Execution log of all automated and operator-approved recovery actions, with audit evidence receipts.
- **Experiments (`/dashboard/experiments`):** Multi-run benchmarking engine for evaluating detection latency, recovery time, and safety compliance.
- **Analytics (`/dashboard/analytics`):** Longitudinal reliability trends, incident frequency by service, and SLO burn-rate tracking.
- **Reports (`/dashboard/reports`):** Audit-compliant PDF and JSON report downloads.
- **Settings (`/dashboard/settings`):** User management, RBAC configuration, alert thresholds, and integration webhooks.

## 3. Incident Triage & Resolution Workflow

### Step 1: Discovering Active Incidents
When a service experiences telemetry anomalies (e.g., error rate spike or latency degradation), Prometheus evaluates alert rules and dispatches an alert through Alertmanager to AutoHeal.
1. An incident appears at the top of the **Incidents** list with status `investigating` and a severity badge (`CRITICAL`, `HIGH`, `MEDIUM`, `LOW`).
2. Click on the incident row to open the **Incident Details** view.

### Step 2: Inspecting Evidence & Timeline
The Incident Details view presents three primary tabs:
- **Timeline:** Chronological event feed tracing the exact progression from initial fault detection, alert trigger, AI analysis, to operator actions.
- **Telemetry & Evidence:** Live time-series charts displaying error rate (%), P95 latency (ms), and resource utilization leading up to the incident.
- **AI Diagnosis:** Natural-language analysis generated by Google Gemini (or the deterministic rule engine), highlighting:
  - Root-cause hypothesis.
  - Affected services and downstream blast radius.
  - Confidence score (0.0 to 1.0).
  - Recommended recovery action.

### Step 3: Approving or Rejecting Recovery
If a recovery action is recommended:
1. Review the **Recommended Action** card (e.g., `restart_container`, `restart_pool`, or `scale_service`).
2. Verify that the action parameters and target service match the affected component.
3. Click **Approve Recovery**.
4. In the confirmation modal, enter optional operator notes (e.g., "Approved based on confirmed 503 spike during pilot testing").
5. Click **Confirm Execution**.

> [!NOTE]
> Under `RECOVERY_SIMULATION_MODE=true`, the execution is dispatched to `SimulatedAgentClient`. The agent verifies the cryptographic envelope, checks the strict allowlist, and executes a bounded simulation. No live Docker containers or host processes are altered.

### Step 4: Observing Post-Recovery Verification
Once execution concludes:
1. The `PostRecoveryVerifier` automatically probes the target service telemetry.
2. If metrics normalize below SLO thresholds (e.g., error rate drops from 100% to 0.02%, P95 latency normalizes below 300ms):
   - The recovery status transitions to `Completed / Verified healthy`.
   - The incident status transitions to `resolved`.
   - A success event is appended to the timeline and immutable audit log.
3. If telemetry remains degraded:
   - The recovery status transitions to `Verification failed / Escalation required`.
   - The incident transitions to `escalated`, alerting the on-call engineer.

## 4. Benchmarking & Experimentation Operations

AutoHeal includes a built-in Monte Carlo experiment framework to benchmark MTTR and recovery reliability across controlled scenarios.

### Creating an Experiment
1. Navigate to **Experiments** (`/dashboard/experiments`).
2. Click **New Experiment**.
3. Select an evaluation scenario:
   - **S1: Healthy Baseline:** Nominal workload, zero fault injection (verifies zero false positives).
   - **S2: 503 Outage:** Sustained HTTP 503 availability failure (`restart_container` action).
   - **S3: High Error Rate:** Intermittent HTTP 500 error burst (`restart_pool` action).
   - **S4: Resource Exhaustion:** CPU and memory saturation (`scale_service` action).
   - **S5: Repeated Alerts:** Churning intermittent alerts.
4. Set **Number of Runs** (recommended: `5` for standard pilot benchmarking).
5. Specify **Random Seed** (default: `42` for exact reproducibility).
6. Toggle **Recovery Enabled** (`True` to measure recovery MTTR, `False` to measure unmitigated control baseline).
7. Click **Launch Experiment**.

### Reviewing Benchmark Results
Upon completion, the dashboard displays:
- **Per-Run Breakdown:** Detection latency, dispatch delay (200 ms), recovery duration, verification delay, and total outage duration.
- **Statistical Aggregates:** Min, Max, Mean, Median, Sample Standard Deviation ($s$), Standard Error of the Mean ($SEM = s / \sqrt{N}$), and P95 percentile.
- **Right-Censored Baseline Notice:** Control runs (recovery disabled) display a constant $60,000.0\,\text{ms}$ outage duration, representing the observation cutoff window ($T_{\text{cutoff}}$).

## 5. Report Generation & Audit Exports

1. Navigate to **Reports** (`/dashboard/reports`) or click **Download Report** from any completed Experiment page.
2. Select desired format:
   - **JSON Export:** Complete raw dataset including timestamps, seed, per-run telemetry samples, and cryptographic evidence hashes. Ideal for statistical audits.
   - **PDF Summary:** Formatted executive and engineering report with metric distribution tables and research integrity disclosures.
3. The generated file downloads directly through your browser.
